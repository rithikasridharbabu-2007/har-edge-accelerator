# Project plan

Each phase has a short task list and a "done when" line. A phase is not done until its row in the README results table is filled in from a script anyone can rerun.

Time estimates assume about 6 to 8 hours a week alongside classes. They are guesses; adjust after Phase 1.

## Rules for the whole project

1. **Predict, then measure.** Before building anything in Phases 2 to 5, write the expected number in `docs/predictions.md` with one line on how it was estimated. Never edit a prediction after seeing the result; add a new dated entry instead.
2. **Every number comes from a script.** No hand-copied results.
3. **Keep the model small.** The goal is a finished pipeline, not the best accuracy. If a design choice makes the RTL harder, shrink the model.
4. **Log tool problems.** Any bug, confusing error or missing doc in cocotb, Edalize, Verilator or hls4ml goes in `docs/upstream.md` with a minimal reproduction. These become upstream issues and pull requests.

## Phase 1: Model (about 2 weeks)

- [ ] Script to download and unpack the UCI HAR dataset (raw inertial signals, 128 × 9 per window).
- [ ] Use the dataset's own train/test split, which separates volunteers, so results are comparable with published ones.
- [ ] Train a small 1D CNN in PyTorch. Starting point: two convolution layers, ReLU, max-pool, one dense layer, six outputs. Target under 10,000 parameters.
- [ ] Report test accuracy and a confusion matrix.
- [ ] Count parameters and multiply-accumulate operations per window; these feed the hardware predictions.
- [ ] Export weights to a plain file format (`.npz`).
- [ ] Fix random seeds and pin package versions.

**Done when:** one command trains the model and prints accuracy, parameter count and operation count. Target accuracy: around 90% (a target, not a promise).

## Phase 2: CUDA (about 2 weeks)

Needs an NVIDIA GPU. A Mac has none, so use a lab machine or Google Colab.

- [ ] Write the forward pass by hand in CUDA C++: one kernel for 1D convolution, one for the dense layer.
- [ ] Check outputs against PyTorch on the full test set (floating-point tolerance).
- [ ] Measure latency for batch size 1 and for large batches. Record the GPU model.
- [ ] Measure GPU memory used, and note where it goes.
- [ ] Write down what was learned about batch-1 latency: for a model this small, the GPU is expected to be dominated by launch overhead. Predict this first, then check.

**Done when:** the CUDA row of the results table is filled in and the outputs match PyTorch.

## Phase 3: Quantisation (about 2 weeks)

- [ ] Quantise weights and activations to 8-bit integers. Start with post-training quantisation; move to quantisation-aware training only if accuracy drops more than about 2 points.
- [ ] Choose power-of-two scale factors so hardware can rescale with shifts instead of multipliers.
- [ ] Write a pure-integer reference model in NumPy with no floating point anywhere. This is the specification the hardware must match bit for bit.
- [ ] Decide and document the rounding and saturation rules.
- [ ] Export weights as `.mem` files for Verilog `$readmemh`.
- [ ] Export a set of test vectors: input windows and the expected output of every layer.

**Done when:** the integer reference reproduces the quantised accuracy on the full test set, and test vectors are generated by one command.

## Phase 4: RTL (about 5 to 6 weeks)

Write predictions for LUTs, DSPs, BRAM, maximum clock frequency and cycles per window **before** starting.

- [ ] Architecture note in `docs/architecture.md`: one shared multiply-accumulate unit stepped through the layers by a state machine (small and slow) versus one unit per layer (bigger and faster). Start with the shared unit.
- [ ] Modules, each with its own cocotb test against the Phase 3 vectors:
  - [ ] multiply-accumulate with saturation
  - [ ] weight ROM and activation RAM
  - [ ] 1D convolution layer
  - [ ] max-pool
  - [ ] dense layer and argmax
  - [ ] top-level controller
- [ ] Full-design cocotb test: the whole test set through the Verilog in Verilator, outputs identical to the reference.
- [ ] Edalize build scripts for simulation and for synthesis with Yosys, nextpnr and Apicula targeting the Tang Nano 20K. Confirm the board's resource limits from the Gowin datasheet before sizing the design.
- [ ] GitHub Actions workflow: lint, simulate, synthesise, and publish the resource report.
- [ ] Record measured LUTs, DSPs, BRAM, clock frequency and cycles per window next to the predictions.
- [ ] On the board: stream windows over UART from the laptop, read back the class, and confirm it matches simulation.
- [ ] Energy per window: a USB power meter gives a rough whole-board figure. Label it as rough.

**Done when:** the full test set passes bit-exact in simulation, CI is green, and both RTL rows of the results table are filled in.

## Phase 5 (optional): hls4ml comparison

hls4ml generates code for Xilinx, Intel and similar tools, not for Gowin, and those tools do not run on macOS. This phase needs a Linux lab machine with Vitis HLS, and the comparison is between tool reports for a Xilinx part, not on the Tang Nano. State that clearly in the write-up.

- [ ] Convert the Phase 3 model with hls4ml at the same bit widths.
- [ ] Record its estimated resources and latency.
- [ ] Re-synthesise the hand-written RTL for the same Xilinx part so the comparison is like for like.

**Done when:** the hls4ml row is filled in with the target part named.

## Write-up

- [ ] One diagram of the architecture.

- [ ] Make the repository public once Phase 1 has real results.

## Risks

| Risk | What to do |
|---|---|
| The RTL takes much longer than planned | Cut to one convolution layer plus dense. A finished small design beats an unfinished large one. |
| The design does not fit the board | The shared multiply-accumulate architecture trades speed for area; shrink channel counts next. |
| Quantisation costs too much accuracy | Quantisation-aware training, or 16-bit accumulators with 8-bit weights. |
| No GPU access | Do Phase 2 on Colab, or move it after Phase 4. Nothing later depends on it. |
| Open-source Gowin flow fails on some construct | Log it in `docs/upstream.md`, work around it, and fall back to the Gowin IDE for that build only. |
